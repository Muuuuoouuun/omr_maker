## 3. 선택한 접근

### 3.1 대안

1. 빠른 UI·테스트 보정: UI 점수는 오르지만 보안 최저점 때문에 전체 목표를 달성할 수 없다.
2. **릴리스 하드닝 중심 개선**: 기존 구조를 보존하면서 신뢰 경계, 회귀 검증, UI 계약을 함께 강화한다.
3. Supabase Auth와 데이터 계층 전면 재작성: 장기적으로 타당하지만 이번 목표에 비해 범위와 컷오버 위험이 크다.

선택은 2번이다. 현재의 HMAC 서버 세션과 service-role 서버 액션을 기준으로 데이터 평면을 먼저 닫는다. Supabase Auth 전환은 브라우저가 직접 RLS 데이터를 읽어야 할 때 별도 프로젝트로 진행한다.

## 4. 전체 아키텍처

개선은 다섯 개 독립 슬라이스로 나눈다.

### 4.1 점수 계약과 증거

- 평가 기준을 문서와 테스트 명령으로 고정한다.
- 결과 리포트에는 현재 점수, 변경 근거, 실행 증거, 잔여 위험을 함께 기록한다.
- 자동 테스트만으로 UX나 보안을 과대평가하지 않는다.

### 4.2 UI/UX 집중형 시스템

- 화면마다 primary action은 하나만 둔다.
- 파란색은 진행 행동, 빨간색은 파괴 행동에만 사용한다.
- 8px 단위 토큰을 사용하되 핵심 관계는 16–24px 리듬으로 구성한다.
- 관련 요소 16px, 카드 내부 20–24px, 섹션 간 32–48px을 기본으로 한다.
- 제목은 32/22px, 본문은 16px, 보조 문구는 13px 아래로 내려가지 않는다.
- 모바일에서는 주 행동을 가로 스크롤 뒤에 숨기지 않는다.
- hover는 160ms, 패널·모달은 200–220ms, 이동은 4–8px로 제한한다.
- 반복 루프, 과도한 spring, 장식성 숫자 애니메이션은 사용하지 않는다.
- `prefers-reduced-motion`에서는 즉시 전환한다.
- 모든 모달은 초기 초점, Tab 순환, Escape, 호출점 복귀를 공유 계약으로 갖는다.

### 4.3 릴리스 신뢰성

- 의도된 제품 변경을 따라가지 못한 stale E2E 8건을 현재 계약에 맞춘다.
- PDF 필기 E2E는 실제 PDF/canvas 준비 상태를 기다린 뒤 3회 반복한다.
- Next.js 16.2.12, PostCSS 8.5.23, sharp 0.35.3으로 갱신한다.
- `npm audit --omit=dev --audit-level=high`를 CI blocking gate로 둔다.
- 핵심 server action과 gateway에 커버리지·실패 주입·멱등성 검증을 추가한다.

### 4.4 서버 데이터 경계

- 운영 빌드에서는 publishable-key 기반 canonical CRUD를 만들지 않는다.
- 브라우저 localStorage는 오프라인 캐시로만 사용하고 공식 데이터는 서버 액션을 통과한다.
- 학생 시작코드는 PBKDF2 기반 `omr_student_start_credentials`로 단일화한다.
- 교사 문항 답변, 검토 상태 변경, 강제 종료를 최소 권한 RPC로 분리한다.
- server-only RLS 프로파일은 anon/authenticated canonical 접근을 제거하고 service role RPC만 허용한다.
- readiness probe는 FORCE RLS 존재가 아니라 공개 정책 부재, 권한 회수, 조직 백필을 검증한다.

### 4.5 핵심 워크플로우

- 시험 화면 이탈은 2초 미만이면 폐기한다.
- `window.blur`와 `document.hidden`은 하나의 이탈 세션으로 합친다.
- 2초 이상 이탈은 복귀 시 한 번 기록하며 제출 중 진행 이탈도 누락하지 않는다.
- 학생 경고는 1회 안내, 2회 이상 단계형 경고로 완화한다.
- 교사 화면은 1–2회를 중립, 3회 이상을 주의색으로 표시한다.
- 배포·제출은 로컬 완료와 서버 완료를 구분하고, 재시도 행동과 최종 영수증을 제공한다.

## 5. 데이터 흐름

### 5.1 교사 쓰기

1. UI가 목적별 client wrapper를 호출한다.
2. 서버 액션이 same-origin과 서명 교사 쿠키를 검증한다.
3. 서버가 조직 ID를 세션에서 파생한다.
4. 목적별 service-role RPC가 허용된 필드만 변경한다.
5. 성공 결과와 작업 영수증을 UI에 반환한다.
6. 로컬 캐시는 성공한 서버 결과를 반영한다.

클라이언트가 보낸 `organization_id`, score, 소유자, 기존 question result는 권한 판단이나 공식 값으로 신뢰하지 않는다.

### 5.2 학생 응시와 제출

1. 학생 시작코드를 조직 범위 credential row에서 검증한다.
2. 서버가 서명 학생 세션을 발급한다.
3. 풀이 화면은 정답이 제거된 payload만 받는다.
4. 제출은 답안과 허용된 메타데이터만 서버로 보낸다.
5. 서버가 채점·저장하고 receipt를 반환한다.
6. 네트워크 실패는 목적별 서버 요청 큐로 재생한다. publishable-key table upsert는 재시도하지 않는다.

### 5.3 RLS 컷오버

1. 조직 null·고아 참조·교차 조직 참조를 preflight한다.
2. 스테이징에서 server-only RLS를 적용한다.
3. anon·임의 authenticated·타 조직 공격 시나리오가 모두 거부되는지 검증한다.
4. service-role 전체 여정을 검증한다.
5. 운영 컷오버는 DB·배포 권한자의 별도 승인과 실행 로그를 요구한다.

## 6. 오류 처리

- 보안 준비 상태가 불완전하면 운영 저장을 fail closed한다.
- 서버 오류는 사용자에게 작업 단위 메시지와 재시도 CTA를 제공한다.
- 이미 서버가 확정한 제출·채점 결과는 로컬 재시도로 덮어쓰지 않는다.
- 재시도 요청은 idempotency key를 사용한다.
- 시작코드·세션·조직 불일치는 일반 인증 오류로 노출하고 내부 식별자는 숨긴다.
- PDF·필기 저장 실패는 답안 제출 확정과 분리하되 보류 상태를 명확히 표시한다.
- 중앙 `reportError` 퍼널에 인증 거부, RPC 실패, readiness 실패, 동기화 큐 고착을 연결한다.

## 7. 테스트 전략

모든 동작 변경은 테스트를 먼저 실패시키는 Red–Green–Refactor 순서로 구현한다.

### 7.1 단위·계약 테스트

- 이탈 2초 경계, blur/hidden 중복, 제출 중 이탈
- 목적별 교사 mutation이 허용되지 않은 score/question result를 보존
- production browser boundary에서 Supabase browser client 미생성
- 시작코드 조직 격리와 PBKDF2 검증
- readiness false/true fixture
- UI landmark, focusable upload, dialog focus contract, motion token

### 7.2 브라우저 테스트

- Chromium과 WebKit의 교사·학생 핵심 여정
- PDF 그리기·획 지우개 3회 반복
- 390px 모바일 출제 primary action 노출
- iPad·Galaxy Tab 가로/세로
- 키보드 전용, 200% 확대, reduced-motion
- 시각 회귀 캡처와 콘솔 오류 0

### 7.3 데이터베이스·보안 테스트

- 실제 PostgreSQL에서 schema → migrations → server-only RLS → assertions
- anon/authenticated의 시험·정답·PII·attempt read/write 거부
- service role RPC 성공과 교차 조직 거부
- null org·고아 참조·교차 org 0

### 7.4 완료 검증


## 8. 롤아웃과 롤백

1. 로컬 코드·테스트 개선
2. CI와 의존성 보안 게이트
3. 스테이징 데이터 preflight와 RLS 리허설

## 9. 범위 경계

- 실제 카카오 발송과 실결제는 이번 품질 목표의 필수 기능으로 새로 구현하지 않는다. 화면에서 계획·연동 전 상태를 명확히 표시한다.
- Supabase Auth 전환은 이번 server-only data plane 완성 뒤 별도 프로젝트로 남긴다.
- 운영 DB나 배포 환경 변경은 명시적 대상과 자격 증명이 확인되기 전 실행하지 않는다.
- 대형 페이지 전면 재작성은 하지 않는다. 이번 변경이 닿는 경계를 hook, component, gateway로 분리한다.
