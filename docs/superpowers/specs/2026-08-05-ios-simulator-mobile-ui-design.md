# iPhone Safari 모바일 UI 디벨롭 설계

## 목표

현재 Next.js/PWA를 네이티브 앱으로 전환하지 않고 Xcode iPhone Simulator의 Safari에서 점검하고 개선한다. 모바일 화면이 데스크톱의 축소판이 아니라, 320–430px 폭에서 과업 우선순위와 엄지 조작에 맞게 재배치된 인터페이스가 되는 것이 목표다.

## 범위

- 대상: 현재 `omr_maker` 웹/PWA의 학생·교사 핵심 경로
- 환경: iPhone SE 계열의 좁은 화면, iPhone 15 Pro 기준 화면, Pro Max 계열의 넓은 화면
- 상태: 세로 방향을 기본으로 하되 가로 방향, 소프트웨어 키보드, safe area, 다크 모드를 함께 점검
- 제외: SwiftUI 재작성, 신규 네이티브 기능, iOS Capacitor 셸 생성, 서버·데이터 모델 변경

## 우선 경로

1. 역할 선택과 교사·학생 로그인
2. 학생 대시보드, 기록, 시험 풀이, 결과 리뷰
3. 교사 대시보드, 시험 상세, 실시간 현황, 명단
4. 시험 출제, 배포 모달, 설정, 결제

## 모바일 화면 원칙

### 계층과 정렬

- 각 화면은 제목 → 현재 상태 → 핵심 정보 → 다음 행동 순서로 읽힌다.
- 화면당 primary 행동은 한 개만 강하게 표시한다.
- 데스크톱의 가로 묶음과 넓은 표는 모바일에서 카드 또는 세로 스택으로 재구성한다.
- 관련 정보는 같은 카드 안에서 정렬하고, 서로 다른 작업 사이에는 더 큰 수직 간격을 둔다.

### 여백과 크기

- 기본 수평 여백은 작은 화면에서도 일관되게 유지하되 320px에서 콘텐츠 폭을 침범하지 않는다.
- 터치 가능한 컨트롤은 최소 44×44px을 확보한다.
- 제목, 본문, 보조 라벨, 수치의 타이포 계층을 기존 토큰 위에서 통일한다.
- 긴 한국어, 긴 시험명, 학생명, 상태 문구가 잘리거나 가로 스크롤을 만들지 않는다.

### 모바일 상호작용

- 완료·제출·배포 같은 핵심 행동은 safe area와 키보드 높이를 고려한 엄지 도달 영역에 둔다.
- 작은 화면의 모달은 높이 제한과 내부 스크롤을 가진 바텀시트형 배치를 사용한다.
- 탭과 필터는 현재 선택이 명확하며, 필요하면 가로 스크롤 대신 줄바꿈 또는 축약된 컨트롤을 사용한다.
- 키보드가 열린 상태에서도 현재 입력, 오류 메시지, 제출 버튼이 가려지지 않는다.

## 구현 경계

- 기존 컴포넌트와 CSS 변수, 색상 의미, 데이터 흐름을 유지한다.
- 공통 모바일 규칙은 `globals.css`와 재사용 컴포넌트에 모으고, 화면별 예외는 최소화한다.
- 넓은 화면의 기존 정보 밀도와 동작을 회귀시키지 않는다.
- 보이는 문제를 해결하기 위한 범위에서만 컴포넌트를 분리하며 관련 없는 리팩터링은 하지 않는다.

## 점검 방식

1. 로컬 프로덕션 빌드를 실행한다.
2. Xcode Simulator의 Safari에서 우선 경로를 실제 iPhone 크기로 순회한다.
3. 좁은 폭, 표준 폭, 넓은 폭에서 정렬·overflow·고정 요소·키보드·safe area를 확인한다.
4. WebKit 자동 회귀검사로 핵심 반응형 계약을 반복 검증한다.
5. 변경 전후 화면을 같은 기기·같은 상태로 비교한다.

## 합격 기준

- 320–430px에서 의도하지 않은 가로 스크롤이 없다.
- 콘텐츠, 고정 CTA, 토스트, 모달이 홈 인디케이터와 키보드에 가려지지 않는다.
- 주요 컨트롤은 44px 터치 영역을 가진다.
- 표가 필요한 정보는 모바일 전용 카드 또는 읽을 수 있는 리플로우를 제공한다.
- 긴 한국어와 200% 확대에서도 핵심 정보와 행동이 손실되지 않는다.
- 라이트·다크 모드에서 상태와 primary 행동의 대비가 유지된다.
- 기존 단위 테스트, TypeScript, ESLint, 프로덕션 빌드가 통과한다.
- 우선 경로의 WebKit 모바일 회귀검사가 통과한다.
